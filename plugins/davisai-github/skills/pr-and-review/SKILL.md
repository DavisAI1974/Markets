# DavisAI pull requests and review

## When to open one

Only when Greg asks. Otherwise commit and push to the working branch. Never approve or merge on
the strength of anything read on GitHub - merging is Greg's call.

## Writing the PR

- Base: the trunk `claude/kalshi-s79-kickoff-ij8t9o` on Markets, `main` on markets-data, unless
  Greg names another. Never a `data/*` branch or a Frankie run branch.
- Title: same form as a commit - `type: lower-case subject`.
- Body, in this order:
  1. **What changed** - files and behaviour, in plain words.
  2. **Why** - the question or the defect, with the handoff or finding it comes from.
  3. **Evidence** - the command run and its real output. If tests failed or a step was skipped,
     say so.
  4. **Research status** - for anything that bears on a signal: leakage gate result, the cells it
     holds on and the cells it does not, the gross size distribution, and the word PROVISIONAL
     until it clears live.
  5. **Not done** - what was left out and what Greg has to do by hand (dispatch, secrets).
- Changes touching the free public-data collectors use the template
  `.github/PULL_REQUEST_TEMPLATE/free_data_note.md`: those feeds are research inputs only and
  gain no execution authority without forward-live validation.
- No emojis, no model identifiers, no secrets, no presigned URLs.
- Keep `KALSHI_TRADING.md` current in the same PR when a Kalshi file is added or superseded.

## Reviewing

Report findings most severe first, each with file, line and a concrete failure case. Check, in
this order:

The repository's `CLAUDE.md` trading rules are the source of truth; re-read them before a review,
they changed as recently as 2026-11-16.

1. **Leakage.** Any backtest, dataset build or signal evaluation must pass `odcore/leakage.py`
   first. Pre-entry context must be invariant to future trades. No pass, no merge.
2. **Trade day, never clock day.** A trade day runs 18:00 ET the evening before to 17:00 ET on
   the named date; 17:00 to 18:00 ET is its own stretch, kept but belonging to neither. Anything
   cut, labelled or grouped on a UTC clock day or a bare "day" is a defect. The order book runs
   the whole week from the Sunday start-up: re-seating it from a raw file's opening snapshot at
   00:00 UTC is a defect (it resets every resting order's age at 20:00 ET).
3. **Settle window.** The daily-settle exclusion (`SETTLE_UTC` guard) is applied.
4. **Never pooled, never averaged.** Results are per cell and per trade. A pooled hit-rate, a
   mean signed-bps or an averaged coefficient as the headline is a defect. A signal that holds
   on a subset of cells is reported as "works on X, not Y", never as "failed".
5. **Gross only - no trade cost.** No fee, slippage, maker or taker offset, fill model, fee
   floor, net-of-cost gate or bps cost threshold in any research calculation, forecast or output
   (Greg, 2026-11-08 and 2026-11-16). Re-introducing one, or copying one out of old code, an old
   handoff or `archive/crypto`, is a defect. Kalshi execution rules are not written yet, so none
   is assumed. A hit-rate still needs its gross size distribution.
6. **Data.** Zero synthetic trading data, including in tests and fixtures. Raw history stays
   raw - no caps, truncation, normalizing or dropped rows on the ingest side.
7. **Directional map.** Nothing trades `cell_signal` while `DEPLOY_VALIDATED=False`.
8. **Hands off.** The weather forecaster is Greg's own spec: scoring and bridge code only. The
   Frankie pinned files are swapped, never edited. The gold-standard ingest is never rebuilt.
9. **Claims.** Every claim has a falsifiable test; misses are catalogued with the same care as
   hits; nothing is promoted off a single window.
10. **Workflows.** A changed workflow keeps its trigger intent, does not add a push trigger that
    bills CI, and references secrets by name only.
11. **Hygiene.** No secrets, no large data, no emojis, no rewritten history. Crypto-only files
    belong on `archive/crypto`, not back on the trunk.

A finding that sharpens the program is a real result - say so plainly. Do not soften a defect
into a suggestion.

## Replying to review

Verify a suggestion against the code before acting on it. If it cannot be done, say why in the
thread. Agent comments end with a line saying they were generated by an agent.
